# REOS SuperApp: From Dashboard to Continuity System

## The decisive product change

ListedKit demonstrates a strong interaction truth: work should not disappear when the user asks AI for help. REOS should keep that simultaneous visibility, but its differentiation cannot be a better chat pane. REOS wins when ATLAS carries an outcome across documents, email, people, dates, permissions, and failures—then proves the outcome.

The category statement becomes:

> REOS is the continuity system for every property event. ATLAS turns verified evidence into coordinated, recoverable work.

The north-star metric is **trusted outcomes completed per active property**, not messages sent, tasks created, or features visited.

## First-principles reconstruction

The operator does not fundamentally need more dashboards. They need five things:

- to know what could cause harm;
- to know what must move today;
- to know what is waiting on another person;
- to know what ATLAS already handled;
- to know whether the result is true, authorized, and reversible.

Every primary REOS surface should answer those questions before exposing module navigation. The SuperApp is not “everything in one menu.” It is one shared property-event graph, one attention model, and one safe action protocol rendered through the right context.

## The ATLAS Continuity Loop

Every meaningful ATLAS goal becomes a durable run, not an isolated chat turn.

1. **Sense** — ingest the user goal, property context, new evidence, and the desired outcome.
2. **Resolve** — identify canonical facts, evidence conflicts, freshness, authority, and missing prerequisites.
3. **Plan** — choose a bounded action path plus permitted fallback paths before acting.
4. **Act** — execute the lowest-risk useful step automatically inside the current permit boundary.
5. **Verify** — prove the result against source evidence and the intended outcome.
6. **Recover** — classify failures, try a safe alternate path, or escalate one precise blocker with context preserved.
7. **Report** — produce an ATLAS Receipt, update memory, and include the outcome in the next relevant signal.

This is self-healing without theater. REOS never exposes private chain of thought. It exposes the operational trace: goal, evidence, attempted path, failure class, recovery path, verification, authority, receipt, and undo.

## What “self-healing” requires underneath

### Durable run ledger

Each run stores goal, property, current stage, evidence dependencies, authority boundary, attempts, failure class, fallback candidates, verification condition, next wake time, and final receipt. A browser refresh or worker restart cannot erase the run.

### Failure taxonomy

ATLAS needs explicit classes instead of one generic error:

- source unavailable;
- permission missing;
- ambiguous identity;
- evidence conflict;
- stale integration;
- transient service failure;
- unsupported operation;
- human judgment required.

Each class maps to allowed retries, alternate tools, backoff, and escalation copy.

### Capability router

ATLAS should choose among document evidence, Gmail evidence, calendar state, transaction facts, participant history, integration APIs, and manual request—without repeatedly asking the user for information REOS already has.

### Verification gate

“Tool returned success” is not completion. Completion requires the post-condition: the receipt exists, the milestone state agrees, the authoritative evidence is attached, and cross-surface counts reconcile.

### Recovery memory

When “lender portal unavailable → signed email attachment verified” works for a brokerage, ATLAS remembers the pattern as a candidate fallback. It does not silently generalize authority; it proposes or reuses only within the same proven boundary.

## The Signal System

Periodic email should feel like REOS is paying attention between logins, not filling an engagement quota.

### Operating alerts

These are high-signal, property-specific, and preference-controlled.

- **Event risk:** immediate only when a deadline, money movement, evidence conflict, or client promise crosses a risk threshold.
- **Daily command brief:** one morning digest of prevent-harm items, moves ATLAS completed, precise approvals needed, and today’s closings.

### Operating intelligence

- **Weekly intelligence review:** throughput, prevented risks, recurring blockers, contacts learned, templates that drifted, and one recommended system improvement.
- **Monthly business review:** closings, cycle time, exception rate, workload capacity, and economic value created by ATLAS.

### Product updates

- **System update:** concise release note tied to an operator job, with “what changed / why it matters / whether you need to act.”
- **Field note:** occasional research or benchmark email based on anonymized, aggregate patterns—never disguised as an urgent operating alert.

### Marketing

Marketing and education use a separate consent and sender class. They never borrow the visual urgency, subject-line conventions, or notification channel of operating alerts.

### Email guardrails

- One event may create one message, not one message per subsystem.
- If the user resolves an issue in-app, the queued alert cancels.
- Every recurring signal has an in-message frequency control.
- Empty briefs do not send “nothing happened” spam; the next brief can simply say the system remained clear.
- Every claim links to its source or receipt.

## The interface system

### Five destinations, not twenty modules

- **Today** — the shared attention model.
- **Deals** — transaction and listing workspaces.
- **People** — clients, partners, vendors, and relationship memory.
- **Signals** — operating communication and intelligence cadence.
- **System** — integrations, truth health, permits, preferences, and audit.

Everything else is a contextual tool inside one of these destinations.

### The split screen

The left and center answer “what is happening?” The persistent ATLAS pane answers “what is the system doing about it?” The continuity rail at the seam lets an operator visually follow a queue item into evidence, action, recovery, and receipt.

### The ATLAS Receipt

Every meaningful action exposes:

- outcome;
- supporting evidence;
- confidence and conflicts;
- authority used;
- completion time;
- downstream records changed;
- undo or correction path where safe.

## Roadmap

### Horizon 1 — Continuity kernel (0–30 days)

- Create the durable ATLAS run ledger and failure taxonomy.
- Make contract extraction, inbox reconciliation, and brief generation use one run state.
- Add deterministic retry, alternate-source selection, and precise escalation.
- Emit receipts for every existing ATLAS action.

### Horizon 2 — Own the operator day (30–90 days)

- Replace long dashboard sections with Prevent harm / Move today / Waiting / ATLAS handled.
- Ship the persistent ATLAS pane and continuity rail.
- Launch event-risk alerts and the daily command brief with cancellation/deduplication.
- Instrument trusted outcomes, recovery rate, false escalation rate, and undo rate.

### Horizon 3 — Compounding intelligence (3–6 months)

- Add weekly operating intelligence and brokerage pattern memory.
- Recommend template, vendor, and process improvements from verified outcomes.
- Let users promote proven recovery patterns within explicit permit boundaries.
- Expand the property-event graph beyond transactions into repairs, insurance, utilities, and ownership operations.

### Horizon 4 — The real-estate network OS (6–18 months)

- Give scoped participants a property-specific action surface instead of another portal inbox.
- Let evidence and obligations move across brokerages, title, lenders, contractors, and clients with shared receipts.
- Open a governed capability marketplace where integrations act through the same evidence, permit, verification, and recovery protocol.

## What not to do

- Do not add another global chatbot that forgets the last failure.
- Do not equate more navigation with a SuperApp.
- Do not send product marketing through the risk-alert channel.
- Do not hide uncertainty behind polished prose.
- Do not make the user press “scan” to start work that should already be running.
- Do not silently apply conflicted, low-confidence, or high-consequence facts.

## The moat

The moat is not the model. It is the accumulated, permissioned record of how real property work reaches verified completion: which evidence resolved which obligation, which recovery path worked, which authority allowed it, and what the outcome changed. The mockup makes that invisible system legible.
